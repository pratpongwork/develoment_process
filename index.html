👨‍💼 Project Manager

Project Manager หรือ PM คือคนที่คุมภาพรวมของโปรเจกต์ คอยประสานงานระหว่างทีมและลูกค้า

  • วางแผน Sprint และ Timeline
  • จัดลำดับความสำคัญของงาน (Prioritize)
  • ติดตามความคืบหน้าของโปรเจกต์
  • สื่อสารกับลูกค้าและ Stakeholders
  • ช่วยแก้ปัญหาและตัดสินใจเมื่อมีอุปสรรค

👨‍💻 Developer

นักพัฒนาซอฟต์แวร์ (Dev) มีหน้าที่ในการเขียนโค้ดให้ระบบทำงานตามที่ออกแบบไว้

  • แปลง Requirement เป็นโค้ด
  • เขียนฟีเจอร์ใหม่และแก้ไขบั๊ก
  • ใช้ Git สำหรับ version control
  • ทำงานร่วมกับ Designer และ Tester
  • Review โค้ดของเพื่อนร่วมทีม

🎨 Designer

Designer จะรับผิดชอบด้านประสบการณ์ผู้ใช้ (UX) และหน้าตาระบบ (UI)

  • วิเคราะห์ความต้องการของผู้ใช้
  • ออกแบบ Flow การใช้งานและ Wireframe
  • สร้าง UI ด้วย Figma หรือเครื่องมืออื่น
  • ทำงานร่วมกับ Dev เพื่อส่งมอบดีไซน์
  • ตรวจสอบการ Implement ให้ตรงกับดีไซน์

🚀 DevOps

DevOps คือผู้เชื่อมต่อระหว่างการพัฒนาและการนำระบบขึ้นใช้งานจริง

  • ดูแลระบบเซิร์ฟเวอร์และโครงสร้างพื้นฐาน
  • ตั้งค่า CI/CD สำหรับการ deploy อัตโนมัติ
  • ตรวจสอบความปลอดภัยของระบบ
  • แก้ไขปัญหาที่เกี่ยวกับ environment
  • ทำให้ระบบมีเสถียรภาพและสเกลได้

💡 Tester (QA)

Tester หรือ QA (Quality Assurance) มีหน้าที่ตรวจสอบคุณภาพของระบบก่อนนำไปใช้งานจริง

  • วางแผนการทดสอบตาม Requirement
  • ทดสอบฟีเจอร์ต่าง ๆ และรายงานบั๊ก
  • ทำ Regression Test เมื่อมีการเปลี่ยนแปลง
  • ทำงานใกล้ชิดกับ Dev และ PM
  • ช่วยให้มั่นใจว่าระบบพร้อมใช้งานจริง

🛠️ เครื่องมือที่ทีมของเราใช้

  • การสื่อสารภายในทีม: Microsoft Teams
  • จัดการงานและติดตามความคืบหน้า: Azure DevOps Boards
  • จัดเก็บและจัดการ source code: Azure DevOps Repos
  • กระบวนการ Build และ Deploy (CI/CD): Azure DevOps Pipelines
  • ออกแบบ UX/UI: Figma
  • การเขียน Test Case และตรวจสอบคุณภาพ: Google Sheets, New Banana Testing

🏗️ Foundation Meeting

ก่อนเริ่ม Sprint แรก เราจะมี Foundation Meeting เพื่อให้ทุกฝ่ายเข้าใจเป้าหมายและมาตรฐานเดียวกัน

  • ยืนยันวิสัยทัศน์ โปรดักต์ Goal และตัวชี้วัดความสำเร็จร่วมกัน
  • สรุปขอบเขตงาน (Scope) และ MVP ที่ต้องส่งมอบในระยะสั้น
  • วางแผนโครงสร้างทีม ระบุ Stakeholder และช่องทางการสื่อสาร
  • กำหนด Definition of Ready / Definition of Done ที่ทุกคนยึดตาม
  • เตรียม Roadmap ระดับสูง และจัดลำดับ Backlog ก่อนเข้าสู่ Sprint Planning

✅ Definition of Ready (DoR) & ✅ Definition of Done (DoD)

ตั้งเกณฑ์เดียวกันก่อนเริ่มและก่อนจบงาน เพื่อให้ส่งมอบได้คุณภาพสม่ำเสมอ

  • DoR ตัวอย่าง: มี User Story + Acceptance Criteria, UX พร้อม, Dependency เคลียร์, Estimation เสร็จ
  • DoD ตัวอย่าง: ผ่าน Code Review, Unit/Integration test เขียว, QA ผ่านตาม AC, Deploy ไป Staging พร้อม Release note

🏗️ Foundation Meeting — Project Manager (PM)

Project Manager เป็นผู้นำการประชุมเพื่อวางภาพใหญ่ของโปรเจกต์

  • เตรียม User Story, Timeline เบื้องต้น และ Scope ที่ตกลงกับลูกค้า
  • รวบรวม Vision Deck, Persona, Journey เพื่ออธิบายปัญหาและเป้าหมาย
  • สรุป Stakeholder หลัก ช่องทางสื่อสาร และ expectation ของแต่ละฝ่าย
  • Present Roadmap ระดับสูง พร้อม Milestone สำคัญและความเสี่ยงที่คาดการณ์ไว้
  • เก็บ Action Item ที่ต้อง follow up ก่อนเข้าสู่ Sprint แรก

🏗️ Foundation Meeting — Designer

ทีมดีไซน์ช่วยวางภาพประสบการณ์ผู้ใช้และแนวทางการออกแบบ

  • เตรียม Story Book, Design Guideline ที่ใช้ร่วมกับแบรนด์
  • แสดง Concept Wireframe หรือ Flow คร่าว ๆ ของจุดสำคัญ
  • รวบรวม Feedback ที่ได้รับจากลูกค้าก่อนหน้า เพื่อจับจุดที่ต้องโฟกัส
  • ระบุความต้องการด้าน Assets / Components ที่จะต้องใช้ใน Sprint แรก
  • เสนอวิธีทำงานร่วมกับ Dev และ QA เช่น ช่องทาง REVIEW ดีไซน์, Definition of Ready สำหรับงาน UI

🏗️ Foundation Meeting — Technical / Dev

Technical Lead และทีม Dev กำหนดแนวทางเทคโนโลยีและการพัฒนา

  • เสนอ Architecture Diagram, Integration Points และ Dependency สำคัญ
  • วิเคราะห์ความเสี่ยงทางเทคนิค พร้อมเสนอ Spike หรือ Proof of Concept ที่ต้องทำ
  • ยืนยัน Tech Stack, Coding Guideline, Branching Strategy และเครื่องมือหลัก
  • ระบุ Resource หรือ Environment ที่ต้องเตรียม เช่น Cloud, Database
  • สื่อสาร Definition of Done ทางเทคนิค เช่น Unit Test Coverage, Code Review Criteria

🏗️ Foundation Meeting — DevOps

DevOps เตรียมระบบพื้นฐานและความพร้อมสำหรับการส่งมอบงานตั้งแต่วันแรก

  • กำหนด Infrastructure Overview, Environment ที่ต้องใช้ (Dev/Staging/Prod)
  • เตรียม CI/CD Pipeline เบื้องต้น พร้อมเครื่องมือ Deploy/Monitoring
  • ยืนยันแนวทาง Security, Backup, Access Control ร่วมกับทีมเทคนิค
  • รวบรวมความต้องการด้าน Resources เช่น cloud quota, domain, SSL
  • วางแผน Incident Response และช่องทางการ Support หลัง go-live

🏗️ Foundation Meeting — QA / Tester

QA ช่วยกำหนดมาตรฐานคุณภาพและแผนการทดสอบตั้งแต่ต้น

  • จัดทำ Test Strategy, Quality Gate และประเภทการทดสอบที่จะใช้
  • กำหนด Test Environment, Test Data และเครื่องมือที่ต้องเตรียม
  • เสนอแนวทาง Automation / Manual test ที่ต้องทำในระยะสั้น
  • สรุปรายการ Risk หรือ Constraints ที่เกี่ยวข้องกับ QA ให้ทีมรับทราบ

🔁 Agile Process ที่เราใช้

กระบวนการทำงานของเรายึดหลัก Agile ที่เน้นการทำงานเป็นรอบสั้น ๆ เรียกว่า "Sprint" เพื่อให้สามารถปรับตัวและพัฒนาได้อย่างรวดเร็วตามความต้องการของลูกค้า

  • 1. Sprint Planning: ทีมจะวางแผนร่วมกันว่าในรอบนี้จะทำอะไรบ้าง
  • 2. Daily Stand-up: ทุกเช้าจะประชุมสั้น ๆ เพื่ออัปเดตสถานะ ปัญหา และสิ่งที่จะทำต่อ
  • 3. Development: Developer ทำการเขียนโค้ดตาม task ที่ได้รับมอบหมาย
  • 4. Testing: Tester ทำการทดสอบ ตรวจสอบคุณภาพงาน และรายงานปัญหา
  • 5. Review: แสดงผลงานของ Sprint ให้ทีมและผู้เกี่ยวข้องดู
  • 6. Retrospective: สรุปสิ่งที่ดี สิ่งที่ควรปรับปรุงใน Sprint ที่ผ่านมา

การทำงานแบบ Agile ช่วยให้ทีมเรายืดหยุ่น ปรับตัวได้เร็ว และส่งมอบงานได้มีประสิทธิภาพมากขึ้น

👨‍💼 Project Manager ใน Sprint

  • วางแผน Sprint ร่วมกับทีม
  • จัดลำดับความสำคัญของงาน (Prioritization)
  • ติดตามความคืบหน้า และแก้ไขอุปสรรคต่าง ๆ
  • อัปเดตลูกค้าและ Stakeholders

👨‍💻 Developer ใน Sprint

  • แปลง Requirement เป็นโค้ดที่ทำงานได้จริง
  • ทำ Pair programming หรือ Review โค้ดเพื่อนร่วมทีม
  • เขียน Unit Test และแก้ไขบั๊ก
  • ส่งงานผ่าน Git และ Merge เข้าระบบ

🎨 Designer ใน Sprint

  • ออกแบบหน้าจอและ UX สำหรับฟีเจอร์ใหม่
  • ปรับแก้ดีไซน์ตาม Feedback จากทีม
  • ส่งมอบ UI ที่พร้อมให้ Dev ใช้งาน
  • ตรวจสอบว่า Dev ทำตรงตามแบบหรือไม่

🚀 DevOps ใน Sprint

  • ดูแลระบบ CI/CD ให้พร้อมใช้งาน
  • Deploy ระบบขึ้น staging หรือ production
  • จัดการ Environment และ Database
  • ช่วยทีมแก้ปัญหาด้าน Infrastructure

💡 Tester (QA) ใน Sprint

  • วางแผนและเขียน Test Cases
  • ทดสอบ Manual และ Automation
  • รายงานบั๊ก และติดตามการแก้ไข
  • ช่วยตรวจสอบก่อนระบบขึ้น UAT หรือ Production

📦 การส่งมอบงาน และ Release

หลังจากจบแต่ละ Sprint ทีมจะมีการเตรียมส่งมอบงานให้ลูกค้าอย่างเป็นระบบ:

  • Demo: PM และทีม Dev จะสาธิตผลงานจาก Sprint ให้ลูกค้าเห็นสิ่งที่พัฒนาไป
  • UAT (User Acceptance Test): ลูกค้าได้ทดลองใช้งาน และให้ Feedback
  • ปรับปรุงตาม Feedback: ทีมจะนำสิ่งที่ได้ไปแก้ไขหรือต่อยอดใน Sprint ถัดไป
  • Release: งานที่ผ่าน UAT แล้วจะถูก deploy ไปยัง Production หรือใช้งานจริง

ระบบของเรามีการแบ่งเวอร์ชันการส่งมอบ เช่น:

  • Staging: ทดสอบภายในทีม
  • UAT: ทดสอบกับลูกค้าในสภาพแวดล้อมจำลองจริง
  • Production: เวอร์ชันที่พร้อมใช้งานจริง

ลูกค้าจะได้รับงานที่ผ่านการทดสอบ และมีเอกสารประกอบหรือคู่มือการใช้งานในแต่ละรอบ Release

📌 การแบ่งรอบ Release และเลขเวอร์ชัน

เพื่อให้การส่งมอบงานเป็นระบบ ทีมเรามีการจัดการรอบ Release และกำหนดเวอร์ชันให้ชัดเจน:

  • Staging: ใช้สำหรับการทดสอบภายในทีม
  • UAT (User Acceptance Test): ส่งให้ลูกค้าทดสอบบนสภาพแวดล้อมที่ใกล้เคียง Production
  • Production: เวอร์ชันที่พร้อมใช้งานจริง

ตัวอย่างการตั้งชื่อเวอร์ชัน:

  • v1.0.0 - เวอร์ชันแรกที่พร้อมใช้งาน
  • v1.1.0 - เพิ่มฟีเจอร์ใหม่
  • v1.1.1 - แก้ไขบั๊กเล็กน้อย

รูปแบบนี้เรียกว่า Semantic Versioning: MAJOR.MINOR.PATCH

🔄 Aftermath (Retrospective)

เมื่อปล่อยงานแล้ว ทีมจะกลับมาทบทวนสิ่งที่เกิดขึ้นใน Sprint เพื่อเรียนรู้และพัฒนาต่อ

  • สะท้อนสิ่งที่ทำได้ดี สิ่งที่ติดขัด และอะไรที่อยากลองทำในรอบหน้า
  • รวบรวม Feedback จากลูกค้าและสมาชิกทีม แล้วจัดลำดับ Action Item
  • กำหนดผู้รับผิดชอบและกำหนดเส้นตายของ Action Item แต่ละข้อ
  • อัปเดต Process/Tooling ให้เหมาะสม เช่น ปรับ flow, test coverage, automation
  • ฉลองความสำเร็จเล็ก ๆ น้อย ๆ เพื่อรักษาขวัญและกำลังใจทีม

การ Retrospective ที่สม่ำเสมอช่วยให้ทีมเติบโต และปล่อยงานได้คุณภาพมากขึ้นในทุก ๆ Sprint

FOR YOUR INFOMATION

🌳 Branching Strategy

  • Trunk-based (แนะนำ): main เสถียร, feature branches สั้น, PR เล็ก, CI เข้ม
  • GitFlow: ใช้เมื่อมี release cadence ชัดเจนและหลายสภาพแวดล้อม
  • ตั้ง naming มาตรฐาน เช่น feature/, fix/, release/
  • ไม่ push ตรง main; ใช้ PR + Review + CI เท่านั้น

🔍 Code Review Checklist

  • ความถูกต้องตาม AC, test ครอบคลุม, แฮนด์ล error และ edge cases
  • อ่านง่าย แยกความรับผิดชอบ, ฟังก์ชันสั้น, ตั้งชื่อสื่อความหมาย
  • ผลกระทบด้าน performance, security, accessibility
  • คงสไตล์ทีม (lint/formatter), commit message ชัดเจน

🧾 Issue Lifecycle

  • To Do → In Progress → In Review → QA → Ready for UAT → Done
  • Definition ของแต่ละสถานะชัดเจน เพื่อลดการตีความ
  • ทุกการเคลื่อนไหร่มาพร้อมหลักฐาน: PR link, screenshot, test link

🧪 Test Pyramid & Quality Gates

  • Unit (มาก) → Integration (พอเหมาะ) → E2E/UI (เฉพาะ critical path)
  • CI gate: lint, test, coverage threshold, build artifact
  • UAT gate: AC ผ่าน, regression สำคัญเขียว, no P1 bug

🔐 Security Basics

  • ห้าม hardcode secret; ใช้ secret manager / env
  • การยืนยันตัวตน/สิทธิ์เข้าถึง, audit log สำหรับ action สำคัญ
  • Dependency scanning, SAST/DAST (ถ้ามี)

📈 Performance & Observability

  • ตั้ง performance budget (TTFB/LCP/CLS หรือ API latency)
  • Log โครงสร้าง, tracing, metrics + alerting ที่สำคัญ
  • Post-release monitoring + rollback plan

🎯 Intern Expectations & Evaluation

  • Growth mindset: ถาม-ลอง-สรุปบทเรียน
  • คุณภาพก่อนปริมาณ: PR เล็ก มี test, อธิบาย impact
  • วัดผล: attendance, task completion, code quality, teamwork, communication

💬 Communication Norms

  • อัปเดตสั้น-ชัด-ตรงประเด็น: context → ปัญหา → ทางเลือก → ข้อเสนอ
  • เขียนก่อนพูด: ใช้ issue description/PR description ให้ละเอียด
  • เวลาติด: 30 นาทีไม่คืบหน้า ให้ขอความช่วยเหลือ

🔷 Azure DevOps คืออะไร?

ชุดเครื่องมือออนไลน์จาก Microsoft สำหรับจัดการโปรเจกต์ซอฟต์แวร์ครบวงจร

  • 📋 Boards — จัดการ Work Items, Sprint Planning, Kanban
  • 📁 Repos — ที่เก็บ Source Code บน Git (Azure Repos)
  • ⚙️ Pipelines — CI/CD อัตโนมัติ Build & Deploy
  • 🧪 Test Plans — จัดการ Test Cases และ Test Runs
  • 📦 Artifacts — จัดการ Package / Library ของทีม

ทีมของเราใช้ Boards + Repos + Pipelines เป็นหลัก

📋 Boards — มุมมองหลัก

Boards คือส่วนที่ทีมใช้ติดตามและจัดการงานทั้งหมด

  • Work Items — รายการงานทั้งหมดในโปรเจกต์
  • Boards — มุมมอง Kanban Card แสดงสถานะงาน
  • Backlogs — รายการ User Stories / Tasks ที่ยังไม่ได้ทำ
  • Sprints — วางแผนและติดตามงานในแต่ละรอบ Sprint
  • Queries — ค้นหา Work Item ด้วย Filter ต่าง ๆ

🗂️ Work Item Hierarchy

งานในระบบถูกจัดเป็นลำดับชั้นจากใหญ่ไปเล็ก:

  • 🏛️ Epic — เป้าหมายใหญ่ของโปรเจกต์ เช่น "ระบบ Authentication"
  • 🧩 Feature — ฟีเจอร์ภายใน Epic เช่น "Login ด้วย Email"
  • 📖 User Story — มุมมองผู้ใช้: "As a user, I want to..."
  • ✅ Task — งานย่อยที่ Dev/Designer ทำได้จบใน 1–2 วัน
  • 🐛 Bug — ข้อผิดพลาดที่ต้องแก้ไข

ในฐานะ Intern คุณจะรับ Task หรือ Bug เป็นหลัก

✅ วิธีเปิด Task ใหม่ (Step by Step)

  • 1️⃣ ไปที่ Boards → Sprints หรือ Backlogs
  • 2️⃣ คลิก + New Work Item แล้วเลือกประเภท Task (หรือ Bug)
  • 3️⃣ กรอกข้อมูลที่จำเป็น:
    • Title — อธิบายสิ่งที่ต้องทำให้ชัดเจน
    • Assigned To — ระบุผู้รับผิดชอบ
    • Sprint / Iteration — Sprint ที่จะทำงานนี้
    • Description + Acceptance Criteria — รายละเอียดและเกณฑ์ตรวจสอบ
    • Story Points — ประเมินขนาดงาน (ถ้ามี)
  • 4️⃣ กด Save และแจ้งทีมใน Daily Stand-up

🗂️ Sprint Board — การใช้งานประจำวัน

  • ทุกเช้า Daily Stand-up → เปิด Sprint Board ดูภาพรวมงาน
  • ย้าย Card ตามสถานะจริง: To Do → In Progress → In Review → Done
  • อัปเดต Remaining Work เมื่อทำงานแต่ละวัน
  • ถ้าติดปัญหา → ใส่ comment ในงาน และ flag ใน Stand-up ทันที
  • ไม่ควรมี Task ค้างที่ "In Progress" นานเกิน 2–3 วัน โดยไม่มีอัปเดต
  • ปิด Sprint → Task ที่ยังไม่เสร็จหารือกับ PM ว่า Carry Over หรือ Backlog

📁 Azure Repos — Git บน Cloud

Azure Repos คือ Git Repository ที่โฮสต์บน Azure DevOps

  • Files — ดูโครงสร้างไฟล์และ Source Code ใน Branch ปัจจุบัน
  • Commits — ประวัติการเปลี่ยนแปลงโค้ดทั้งหมด
  • Branches — จัดการ Branch ทั้งหมด, ดู Protection Rules
  • Tags — Version tags เช่น v1.0.0, v1.1.0
  • Pull Requests — สร้างและจัดการ PR เพื่อ Merge โค้ด

เข้าถึงได้ที่ Azure DevOps → Repos ในเมนูซ้ายมือ

🔀 Git Workflow ในการทำงานจริง

  • 1️⃣ รับ Task → อ่าน Description และ Acceptance Criteria ให้ครบ
  • 2️⃣ อัปเดตโค้ดล่าสุด → git pull origin main
  • 3️⃣ สร้าง Branch ใหม่ → git checkout -b feature/1234-task-name
  • 4️⃣ เขียนโค้ด → แก้ไขตาม Task, ทดสอบบนเครื่องก่อน
  • 5️⃣ Commit → git add . แล้ว git commit -m "feat: ..."
  • 6️⃣ Push ขึ้น Remote → git push origin feature/1234-task-name
  • 7️⃣ สร้าง Pull Request → บน Azure DevOps เพื่อ Request Review

💻 Git Commands ที่ใช้บ่อย

  • git clone <url> — โคลน Repository มาที่เครื่อง (ทำครั้งแรกครั้งเดียว)
  • git pull origin main — ดึงโค้ดล่าสุดจาก Remote
  • git checkout -b feature/xxx — สร้างและสลับไป Branch ใหม่
  • git status — ดูสถานะไฟล์ที่เปลี่ยนแปลง
  • git add . — Stage ไฟล์ทั้งหมด (หรือระบุชื่อไฟล์)
  • git commit -m "feat: ชื่องาน #ID" — บันทึก Commit
  • git push origin <branch> — Push ขึ้น Remote
  • git log --oneline — ดูประวัติ Commit แบบสั้น
  • git stash / git stash pop — เก็บ/คืนงานที่ทำค้างไว้ชั่วคราว

🌿 Branching Strategy ใน Azure Repos

ตั้งชื่อ Branch ให้สื่อความหมายและเชื่อมกับ Task ID:

  • feature/1234-add-login-page — ฟีเจอร์ใหม่
  • fix/1235-fix-login-button — แก้ Bug
  • hotfix/security-patch — แก้ด่วนใน Production
  • release/v1.2.0 — Branch สำหรับเตรียม Release

กฎสำคัญ:

  • ห้าม push ตรงไปที่ main หรือ develop
  • Branch ควรมีอายุสั้น → Merge กลับภายใน Sprint
  • ลบ Branch ที่ Merge แล้วเสมอ เพื่อไม่ให้รก

🔄 วิธีสร้าง Pull Request (Step by Step)

  • 1️⃣ Push Branch ขึ้น Remote เรียบร้อยแล้ว
  • 2️⃣ ไปที่ Repos → Pull Requests → New Pull Request
  • 3️⃣ เลือก Source branch (branch ที่เพิ่ง push) และ Target branch (เช่น main)
  • 4️⃣ กรอก Title: เช่น feat: Add login page #1234
  • 5️⃣ กรอก Description: อธิบาย What ทำอะไร / Why ทำทำไม / How to test
  • 6️⃣ เพิ่ม Reviewers อย่างน้อย 1 คน
  • 7️⃣ กด Link Work Items → เลือก Task ที่เกี่ยวข้อง
  • 8️⃣ กด Create และแจ้ง Reviewer ใน Teams / Chat

📝 Checklist ก่อน Create PR

  • ✅ Title ชัดเจน: prefix (feat/fix) + สรุปสั้น + Task ID
  • ✅ Description: What ทำอะไร, Why ทำทำไม, How to test
  • ✅ Link Work Item: เชื่อม Task หรือ User Story ที่เกี่ยวข้อง
  • ✅ Reviewers: เพิ่มคน Review อย่างน้อย 1 คน
  • ✅ ไม่มี Merge Conflicts: แก้ conflict ก่อน Request Review
  • ✅ CI ผ่าน: Build และ Test สีเขียวทั้งหมด
  • ✅ PR ขนาดเล็ก: เปลี่ยนน้อยที่สุดเท่าที่จำเป็น → Review ง่ายขึ้น

👀 กระบวนการ Review & Merge

  • 🔍 Reviewer อ่านโค้ด → ตรวจ logic, naming, test, security
  • 💬 Leave Comments → แนะนำสิ่งที่ควรปรับปรุงหรือตั้งคำถาม
  • 🔧 Dev แก้ไข → ตอบ comment หรือ resolve แล้ว push ใหม่
  • ✅ Approve → Reviewer กด Approve เมื่อพอใจแล้ว
  • 🎉 Merge → เมื่อครบ Approvals และ CI ผ่าน → กด Complete
  • 🗑️ Delete Branch → ลบ Feature Branch หลัง Merge แล้ว
  • 🗂️ อัปเดต Task → ย้ายสถานะ Work Item เป็น Done / QA

🔗 การ Link Work Item กับ Commit และ PR

Azure DevOps ช่วยเชื่อมโค้ดกับงานได้อัตโนมัติ:

  • ใน Commit Message: เพิ่ม #<WorkItemID> เช่น feat: Add login form #1234
  • ใน PR: ใช้ปุ่ม "Link Work Items" เพื่อเชื่อม Task ที่เกี่ยวข้อง

ประโยชน์:

  • Traceability — รู้ได้ทันทีว่าโค้ดนี้ทำเพื่อ Task ไหน
  • Task สถานะอัปเดตอัตโนมัติเมื่อ PR ถูก Merge
  • PM / QA ตามความคืบหน้าของงานได้ง่ายขึ้น
  • ย้อนดูได้ว่าแต่ละ feature เริ่ม commit ใน Sprint ไหน

📝 Commit Message Convention

ใช้รูปแบบ Conventional Commits เพื่อให้ประวัติโค้ดอ่านง่าย:

  • feat: Add user login with email #1234
  • fix: Correct validation on login form #1235
  • chore: Update npm dependencies
  • docs: Add API setup guide to README
  • refactor: Extract auth helper to separate file
  • test: Add unit tests for login service

Prefix ที่ใช้บ่อย: feat ฟีเจอร์ใหม่ · fix แก้ Bug · chore งาน maintain · docs เอกสาร · refactor ปรับโค้ด · test เพิ่ม Test

🔁 สรุป Flow การทำงานทั้งหมด

  • 1️⃣ 📋 รับ Task จาก Sprint Board บน Azure Boards
  • 2️⃣ 🌿 สร้าง Branch: git checkout -b feature/<id>-<name>
  • 3️⃣ 💻 เขียนโค้ด บนเครื่อง ทดสอบเบื้องต้น
  • 4️⃣ 📝 Commit: git commit -m "feat: ... #<id>"
  • 5️⃣ ⬆️ Push Branch: git push origin feature/...
  • 6️⃣ 🔄 สร้าง PR บน Azure DevOps + Link Task + เพิ่ม Reviewers
  • 7️⃣ ✅ รอ Review → แก้ Comments → รับ Approve
  • 8️⃣ 🎉 Merge เข้า main → CI/CD Deploy อัตโนมัติ
  • 9️⃣ 🗂️ อัปเดต Task เป็น Done / QA บน Sprint Board

🐙 Git คืออะไร?

Git คือ Version Control System ที่ช่วยให้ทีมพัฒนาโค้ดร่วมกันได้โดยไม่เขียนทับกัน และย้อนกลับได้ทุกเวลา

  • ✅ ติดตามการเปลี่ยนแปลงของทุกไฟล์ใน project
  • ✅ ทำงานได้แบบ offline (local repository)
  • ✅ แยกสาย branch ทำงานคู่ขนานได้
  • ✅ ย้อนกลับสถานะโค้ดได้ทุก commit
  • ✅ ใช้ร่วมกับ Azure Repos, GitHub, GitLab ได้ทันที

🧠 แนวคิดสำคัญใน Git

  • Repository (Repo) — โฟลเดอร์โปรเจกต์ที่ Git ดูแล (มีโฟลเดอร์ .git ซ่อนอยู่)
  • Working Directory — ไฟล์ที่กำลังแก้ไขอยู่บนเครื่อง
  • Staging Area (Index) — พื้นที่เตรียม commit ก่อน (หลัง git add)
  • Commit — snapshot ของโค้ด ณ จุดเวลานั้น พร้อม message และ hash
  • Branch — สายงานคู่ขนาน แยกออกจาก main เพื่อพัฒนาฟีเจอร์
  • Remote — Repository ที่โฮสต์บน cloud เช่น Azure Repos / GitHub

⚙️ ตั้งค่าเริ่มต้น (ทำครั้งเดียว)

git config --global user.name  "ชื่อของคุณ"
git config --global user.email "email@company.com"
git config --global core.editor "code --wait"   # VS Code

Clone repository จาก Azure Repos:

git clone https://dev.azure.com/org/project/_git/repo-name
cd repo-name
  • ตรวจสอบการตั้งค่าด้วย git config --list
  • ดู remote URL ด้วย git remote -v

🔍 ดูสถานะและประวัติ

git status                   # ดูไฟล์ที่เปลี่ยนแปลง
git log --oneline            # ดูประวัติ commit แบบสั้น
git log --oneline --graph    # ดูประวัติแบบ tree
git diff                     # ดูการเปลี่ยนแปลง (ยังไม่ stage)
git diff --staged            # ดูสิ่งที่ stage แล้ว รอ commit
  • git status ควรรันก่อนเสมอก่อนทำอะไรก็ตาม
  • git log --oneline --graph --all ดูภาพรวม branch ทั้งหมด

📝 git add & git commit

git add filename.txt         # stage ไฟล์เดียว
git add src/                 # stage ทั้งโฟลเดอร์
git add .                    # stage ทุกอย่างใน working dir

git commit -m "feat: add login page #1234"
git commit --amend           # แก้ message ของ commit ล่าสุด
                             # (ใช้ได้เฉพาะก่อน push)
  • commit บ่อย ๆ ทีละงานเล็ก ๆ ดีกว่า commit ใหญ่ครั้งเดียว
  • ใช้รูปแบบ feat: / fix: / chore: นำหน้า message เสมอ

⬆️⬇️ git push & git pull

git push origin feature/my-branch    # push branch ขึ้น remote
git push -u origin feature/my-branch # push + set upstream

git pull origin main                  # ดึงโค้ดล่าสุด + merge
git pull --rebase origin main         # ดึงล่าสุด + rebase
git fetch origin                      # ดึง metadata โดยไม่ merge
  • ควร git pull origin main ก่อนเริ่มงานทุกวัน
  • git fetch + git log origin/main ดูก่อนว่ามีอะไรใหม่
  • ห้าม git push --force บน branch ที่คนอื่นใช้ร่วม

🌿 การจัดการ Branch

git branch                     # ดู local branches
git branch -a                  # รวม remote branches
git checkout -b feature/1234   # สร้าง + checkout branch ใหม่
git checkout main              # กลับไป main
git branch -d feature/1234     # ลบ branch (merge แล้วเท่านั้น)
git branch -D feature/old      # บังคับลบ
  • ตั้งชื่อ feature/<id>-description, fix/<id>-description
  • หนึ่ง Task = หนึ่ง Branch เสมอ
  • ลบ branch ที่ merge แล้วเพื่อไม่ให้รกระบบ

🔀 git merge

นำโค้ดจาก branch หนึ่งรวมเข้าอีก branch

git checkout main
git pull origin main          # sync ก่อนเสมอ
git merge feature/1234        # รวม feature เข้า main
git push origin main
  • Fast-forward merge — main ไม่มีโค้ดใหม่ → เลื่อน pointer ได้เลย ไม่สร้าง merge commit
  • 3-way merge — ทั้งสอง branch มีโค้ดใหม่คนละจุด → สร้าง merge commit
  • ในทีม ปกติ Azure DevOps PR จะทำ merge ให้อัตโนมัติหลัง approve

🔄 git rebase

ย้ายฐาน commit ของ branch ให้ต่อจาก commit ล่าสุดของ main — ทำให้ประวัติเป็นเส้นตรง

git checkout feature/1234
git rebase main              # ย้ายฐานมาต่อจาก main ล่าสุด
# (แก้ conflict ถ้ามี แล้วรัน)
git rebase --continue
# หรือยกเลิก:
git rebase --abort
  • ✅ ข้อดี: ประวัติโค้ดเป็นเส้นตรง อ่านง่ายกว่า merge
  • ⚠️ ข้อควรระวัง: อย่า rebase branch ที่ push ขึ้น remote แล้วและมีคนอื่น checkout ไปด้วย
  • 💡 ใช้ก่อนเปิด PR เพื่อ sync กับ main ล่าสุด

⚠️ Merge Conflict คืออะไร?

Conflict เกิดเมื่อ 2 branch แก้ไขบรรทัดเดียวกันของไฟล์เดียวกัน Git ไม่รู้จะเลือกเวอร์ชันไหน จึงให้เราตัดสินเอง

<<<<<<< HEAD  (branch ปัจจุบัน)
Hello from main branch
=======
Hello from feature branch
>>>>>>> feature/1234
  • <<<<<<< HEAD — โค้ดจาก branch ปัจจุบัน
  • ======= — เส้นแบ่งระหว่างสองเวอร์ชัน
  • >>>>>>> feature/1234 — โค้ดจาก branch ที่ merge เข้ามา
  • Conflict ไม่น่ากลัว — แค่เลือก/รวมโค้ดแล้ว commit ต่อได้เลย

🔧 วิธีแก้ Merge Conflict (Step by Step)

  1. รัน git merge feature/1234 → พบ conflict
  2. รัน git status → ดูไฟล์ที่มีปัญหา (แสดงว่า both modified)
  3. เปิดไฟล์ที่ conflict → หาเครื่องหมาย <<<<<<<
  4. แก้ไขโค้ดให้ถูกต้อง → ลบ markers ทั้งหมด (<<<, ===, >>>)
  5. git add <ไฟล์ที่แก้แล้ว> → mark ว่า resolved
  6. git commit -m "merge: resolve conflict in login.ts" → จบ!

💡 VS Code มีปุ่ม "Accept Current / Incoming / Both" ช่วยให้แก้ conflict ได้สะดวกขึ้นมาก

📦 git stash — เก็บงานค้างชั่วคราว

ใช้เมื่อต้องสลับ branch กะทันหันแต่งานยังไม่พร้อม commit

git stash                           # เก็บงานทั้งหมดไว้ก่อน
git stash push -m "WIP: login form" # เก็บพร้อมชื่อกำกับ
git stash list                      # ดูรายการ stash ทั้งหมด
git stash pop                       # นำงานล่าสุดกลับมา + ลบออก
git stash apply stash@{1}           # นำ stash ที่ระบุกลับมา
git stash drop                      # ลบ stash ล่าสุดทิ้ง
git stash clear                     # ลบ stash ทั้งหมด
  • ถ้ามีหลาย stash ให้ใช้ชื่อกำกับ -m ทุกครั้ง

🛠️ Commands ที่ต้องรู้เพิ่มเติม

  • git reset HEAD~1 — ย้อน commit ล่าสุดกลับเป็น staged (โค้ดยังอยู่)
  • git reset --hard HEAD~1 — ย้อนและทิ้งโค้ดด้วย ⚠️ ระวัง!
  • git revert <hash> — สร้าง commit ใหม่เพื่อย้อนผล (ปลอดภัยกว่าบน shared branch)
  • git cherry-pick <hash> — เอา commit เดียวจาก branch อื่นมาใช้
  • git blame filename.txt — ดูว่าแต่ละบรรทัดแก้โดยใคร เมื่อไร
  • git show <hash> — ดูรายละเอียดของ commit นั้น
  • git tag v1.0.0 — สร้าง tag เพื่อระบุ version

🧪 แบบฝึกหัด Git Workshop

ทำครบ 3 exercises เพื่อฝึกสถานการณ์จริงในทีม:

  • 🏋️ Exercise 1 — Clone, สร้าง Branch, Commit, Push (~15 นาที)
  • 🏋️ Exercise 2 — Merge Branch เข้า main (~10 นาที)
  • 🏋️ Exercise 3 — จำลองและแก้ Merge Conflict (~20 นาที)

📁 ใช้ Repository: git-workshop-[ชื่อของคุณ] บน Azure Repos ที่เตรียมไว้

🏋️ Exercise 1 — First Branch & Commit

# 1. Clone repo จาก Azure Repos
git clone <url-จาก-Azure-Repos>
cd git-workshop

# 2. สร้าง branch ใหม่ด้วยชื่อตัวเอง
git checkout -b feature/your-name-intro

# 3. สร้างไฟล์แนะนำตัว
echo "Hi! My name is ..." > introduce.txt

# 4. Commit และ push ขึ้น remote
git add introduce.txt
git commit -m "feat: add introduction for your-name"
git push origin feature/your-name-intro

✅ เป้าหมาย: เห็น branch ของตัวเองปรากฏบน Azure Repos

🏋️ Exercise 2 — Merge Branch

# 1. สลับกลับ main และ sync
git checkout main
git pull origin main

# 2. Merge branch ของตัวเองเข้า main
git merge feature/your-name-intro

# 3. ดูประวัติแบบ graph
git log --oneline --graph

# 4. Push main (หรือเปิด PR บน Azure DevOps)
git push origin main

✅ เป้าหมาย: เข้าใจกระบวนการ merge และดู commit graph ว่าเส้นรวมกันอย่างไร

🏋️ Exercise 3 — Simulate & Resolve Conflict

# คนที่ 1 — แก้ shared.txt บน branch-A
git checkout -b conflict-branch-A
echo "Version from A" > shared.txt
git add . && git commit -m "feat: update shared from A"
git push origin conflict-branch-A

# คนที่ 2 — แก้ shared.txt เดียวกันบน branch-B
git checkout main && git checkout -b conflict-branch-B
echo "Version from B" > shared.txt
git add . && git commit -m "feat: update shared from B"
git push origin conflict-branch-B

# Merge A เข้า main → สำเร็จ ✅
# Merge B เข้า main → CONFLICT! ❌  แก้แล้ว commit ต่อ

✅ เป้าหมาย: เข้าใจว่า conflict เกิดอย่างไร และแก้ได้ด้วยตัวเองโดยไม่ตื่นตระหนก

🎉 สรุป Git Basics

  • 🔁 Daily flow: pull → branch → add → commit → push → PR
  • 🔀 merge รวมโค้ด, rebase จัดเรียงประวัติใหม่ให้เป็นเส้นตรง
  • ⚠️ Conflict ไม่น่ากลัว — เปิดไฟล์ แก้ markers แล้ว git add + commit ต่อได้เลย
  • 📦 stash ช่วยเมื่อต้องสลับงานกะทันหันโดยที่งานยังไม่เสร็จ
  • 🚫 ทุก PR ต้องมาจาก branch เสมอ — ห้าม push ตรง main
